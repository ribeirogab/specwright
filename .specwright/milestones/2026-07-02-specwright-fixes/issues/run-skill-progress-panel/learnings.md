# Run Skill Progress Panel — Learnings

- The approved progress-panel standard has one authoritative source with the exact spec: Gabriel's memory file `progress-panel-standard.md` (colors `#1D9E75` shipped / `#EF9F27` in-flight, 88px chip pill, KPI-row + stacked-bar + issue-list + sub-milestone structure, the `Progresso: ~NN% — X/N shipped · <current> rodando (~NN%) · Y na fila` compact line). The e2e board Conduction notes (line 87) and dossier 8.1 point to it but do not restate the hexes — read the memory file for the transcription, not the board.
- `validate-spec.sh` check 3 trips on a literal double-brace even inside a shell command written *in tasks.md as a step* (e.g. a `grep -nF` guard command that greps for the delimiter). Write such guard commands with a bracket class (`grep -nE '[{][{]'`) so the task file carries no literal double-brace and passes its own check-3 (confirmed: the naive form failed check 3, the bracket-class form passed).
- The head-2/tail-n+3 copy recipe makes canonical and the **scaffold** copy fully byte-identical (both carry `name: sw-run`), while canonical vs the **plugin** copy differ in exactly one line (`name: sw-run` → `name: run`). So AC-5-style "differ only in name:" verification is two different diffs: scaffold expects zero hunks, plugin expects exactly the line-2 hunk.
- Framing renderer-specific content (a `show_widget` reference, hex palette, pt-BR compact-line string) as a *reference example / language-following template* rather than a mandated call keeps a skill section tool-agnostic AND satisfies the `verbatim-evidence` English-only rule — the pt-BR string reads as a documented format instance, not authored non-English prose. This is the pattern for transcribing any locale-specific approved standard into an English skill.
