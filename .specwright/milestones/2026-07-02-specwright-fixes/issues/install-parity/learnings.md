# Install Parity — Learnings

- `sw-spec` and `sw-review-spec` exist in exactly **two** kept-in-sync copies (canonical `.agents/skills/` + scaffold `skills/sw/scaffold/skills/`), unlike the other six companions which have three (plugin `plugins/sw/skills/` as well). Claude Code gets them as plugin **commands** (`plugins/sw/commands/{spec,review-spec}.md`); adding them under `plugins/sw/skills/` would double the slash-menu entries. Do not "fix" the copy count.
- The `/sw:update` reconciliation surface was NOT extended for the two new companions: the managed-set table in all three `sw-update` SKILL.md copies and the hardcoded loop in `skills/sw/scripts/sw-update.sh` (line 64) still enumerate six skills, so `sw-spec`/`sw-review-spec` are never reconciled against upstream. Extending it touches `plugins/` and the skill contract texts — out of install-parity's scope; needs its own change.
- `skills/sw/references/validation.md` (Phase 5) still loops over six skills and checks none of the new install artifacts (`.agents/skills/sw` self-install with executable validator, `.claude/skills/sw` symlink, vault `.gitkeep`s) that `audit-checklist.md` now mandates — deferred to `docs-and-validator`, which stacks on this branch.
- README's "three kept-in-sync copies" claim (line ~83) is now inaccurate for the two-copy pair above — reword in `docs-and-validator`.
- The `.claude/skills/sw` symlink is deliberately created **ungated** on a pre-existing `.claude/` (parity with `install.sh`), while the plugin-settings merge stays gated on `.claude/` existing — two different gating rules in the same Phase 4, both intentional.
- `skills/sw/scripts/{quick_validate,package_skill}.py` need `pyyaml`, which the system `python3` here lacks — run them from a venv (`python3 -m venv && pip install pyyaml`). The repo PR template requires both for any modified skill.
