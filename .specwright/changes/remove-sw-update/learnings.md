# Remove sw:update — Learnings

- **`sw:update` was a leaf capability with no in-plugin callers** — deleting `plugins/sw/skills/update/` and `plugins/sw/scripts/sw-update.sh` required no rewiring. Nothing else under `plugins/sw/` imports the script or references the skill directory; the only coupling was textual (enumerations). Predicted correctly by `plugin-only-restructure`'s learnings, which flagged this issue would "delete this file outright or substantially rewrite" the engine — it was a clean outright deletion.
- **The plugin manifest enumerates companion skills in exactly one place: the `description` string** in `plugins/sw/.claude-plugin/plugin.json`. There is no structured `skills:`/`commands:` array to prune — the only `/sw:*` set enumeration in the manifest is prose inside `description`. A future add/remove of a companion skill must edit that one string; grep the manifest for the skill name to confirm.
- **After this issue ships, every surviving `sw:update`/`sw-update`/`/sw:update` mention in the repo is owned by a *later* sibling, not a dangling reference:**
  - `plugins/sw/references/{agents-md-template,validation,audit-checklist}.md` → owned by `rewrite-sw-init` (rewrites/deletes them once `/sw:init` exists).
  - Root `AGENTS.md`, root `CLAUDE.md`, `README.md`, root `.claude-plugin/marketplace.json`, and `.github/ISSUE_TEMPLATE/{bug,feature_request}.md` → owned by `docs-and-install-flow` (clears the user-facing/root entry-point docs).
  So a repo-wide grep for these strings is expected to be non-empty until both later siblings ship; that is by design, not incomplete work.
- **No unrelated file needed the bare word "update" touched.** `plugins/sw/skills/{review,run}/SKILL.md` and `plugins/sw/skills/brainstorm/scripts/server.cjs` contain ordinary English "update" ("the updated diff", "screen-updated", `crypto ... .update(...)`) — none are `/sw:update` references. Grep for the exact tokens `sw:update|sw-update|/sw:update`, never the bare word, to avoid over-deleting.
- **`tests/install/run.sh` never referenced the update skill or script**, so removing the capability needed zero test edits and the assertion count held at 20/20 (no silent test-integrity drop). When a deletion issue's touched area has tests, re-grep the test file for the removed name before the quality gate to confirm no assertion silently disappears.
- **The AC-3 "grep returns zero matches" bar was delivered as a *conditional* clean sweep** (zero outside 3 named sibling-owned files), and the ticked criterion's own wording must say so — an unconditional "returns zero matches" tick would misrepresent what shipped. This reuses the historical-record carve-out pattern `plugin-only-restructure` established: a repo-wide-grep AC needs its exception set named in the AC text itself, not just in the spec/PR body, or the ticked box and its evidence contradict each other. The review's issue-conformance lane flags exactly that mismatch.
